## 1. DB의 SQL 실행 과정

애플리케이션에서 다음 SQL을 실행한다고 해보자.

```sql
SELECT name
FROM users
WHERE email = 'hello@example.com';
```

이 쿼리문은 users 테이블에서 이메일이 'hello@example.com'인 사용자를 찾아 이름을 반환하라는 의미이다.

그런데 데이터베이스 입장에서 실제 처리하는 과정은 다음과 같다.

1. 요청을 보낸 사용자가 접속할 수 있는 사람인지 확인한다.
2. SQL 문법이 올바른지 검사한다.
3. `users` 테이블과 `email` 컬럼이 실제로 존재하는지 확인한다.
4. 데이터를 어떤 방법으로 찾는 게 가장 효율적인지 결정한다.
5. 결정한 방법대로 데이터를 읽는다.
6. 조회 결과를 애플리케이션에 반환한다.

이와 같은 절차를 담당하는 구성 요소는 아래와 같이 나타낼 수 있다.

```
애플리케이션 (Spring, MySQL Workbench …)
│  SQL 문자열 전송
▼
┌───────────────────── MySQL 서버 엔진 ─────────────────────┐
 ① 연결 관리     커넥션 확인, 사용자 인증, 스레드 할당             
 ② 파서(Parser)  문법 검사 → 파스 트리로 쪼갬                   
                 (SELCT 오타 → 여기서 ERROR 1064)           
 ③ 전처리기      테이블·컬럼이 실제로 있나? 권한 있나?             
                 (없는 컬럼 → 여기서 ERROR 1054)             
 ④ 옵티마이저 ★  "어떻게 읽을까?" 실행 계획 수립                  
                 인덱스를 쓸까, 전체를 읽을까?                  
                 JOIN은 어느 테이블부터?                      
 ⑤ 실행기        실행 계획대로 스토리지 엔진에 데이터 요청            
└─────────────────────────┬───────────────────────────────┘
                          │ Handler API
┌─────────────────────────▼─────────────────────────────────┐
 ⑥ 스토리지 엔진 (InnoDB)                                   
    Buffer Pool(메모리)에 있으면 바로 → 빠름                 
    없으면 디스크에서 읽어 Buffer Pool에 올림 → 느림         
└───────────────────────────────────────────────────────────┘
│  결과 행 반환
▼
애플리케이션
```

| 구성 요소 | 핵심 역할 |
| --- | --- |
| 연결 관리 | 누가 요청했는지 확인 |
| 파서 | SQL 문법 분석 |
| 전처리기 | 테이블, 컬럼, 권한 확인 |
| 옵티마이저 | 가장 효율적인 실행 방법 결정 |
| 실행기 | 실행 계획 수행 |
| 스토리지 엔진 | 실제 데이터 읽기 및 쓰기 |

### **연결 관리**

데이터베이스와 대화할 수 있는 연결을 준비하는 단계이다.

SQL을 데이터베이스로 보내려면 연결이 필요하다.

이때 클라이언트와 서버 사이에 통신할 연결을 먼저 수립해야 한다.

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/shop
    username: app
    password: 1234
```

위 예시를 살펴보면 다음과 같다.

1. 스프링이 mysql로 **연결 요청**을 보낸다.
    
    이때, 접속을 요청할 mysql의 올바른 계정 정보 `username`과 `password`를 함께 보낸다.
    
2. mysql은 연결 하나당 요청 처리를 담당하는 스레드를 할당하여 **연결 수립**을 한다.
    
    이때, 스프링은 여러 개의 연결을 미리 만들어 두는데 이 연결 보관 공간을 커넥션 풀이라고 한다.
    
| 개념 | 의미 |
| --- | --- |
| Connection | 애플리케이션과 DB 사이의 통신 통로 |
| Thread | SQL 실행 등의 작업을 처리하는 실행 흐름 |
| Connection Pool | 재사용할 연결을 보관하는 공간 |
| SQL | 연결을 통해 DB에 전달하는 명령 |

### **파서 (Parser)**

SQL이 올바른 문법으로 작성됐는지 확인하는 단계이다.

```sql
SELECT name
FROM users
WHERE age >= 20;
```

mysql이 SQL을 전달 받을 때, 사람이 읽는 것처럼 이해할 수 없다.

SQL을 구성하는 키워드, 테이블명, 컬럼명, 조건 등을 분석하고 구조화한다.

문법 검사를 통과하면 파스 트리(Parse Tree)를 생성하여 SQL의 구문 구조를 이후 단계에 활용한다.

### **전처리기 (Preprocessor)**

SQL에 사용된 테이블, 컬럼 등이 실제로 존재하는지 확인하는 단계이다.

파서가 SQL 문법을 확인했다면 이번에는 SQL이 실제 데이터베이스에서 실행 가능한지 확인해야 한다.

문법 자체가 올바르더라도 실제 테이블과 컬럼이 존재하지 않을 수 있다.

또한, SQL을 실행하는 사용자가 해당 작업을 수행할 권한이 있는지도 확인한다.

파서와 전처리기는 다음과 같이 구분할 수 있다.

| 구분 | 파서 | 전처리기 |
| --- | --- | --- |
| 검사 대상 | SQL 문법 | 객체 및 권한 |
| 질문 | 문장이 올바른가? | 실제로 존재하고 사용할 수 있는가? |
| 오류 예시 | ERROR 1064 | ERROR 1054 |

### **옵티마이저 (Optimizer)**

데이터를 어떻게 가져오는 것이 가장 효율적일지 결정하는 단계이다.

앞에서 SQL의 검사를 마쳤다면, 실제로 데이터를 가져와야 한다.

그런데 데이터를 가져오는 방법은 여러 가지일 수 있다.

#### **인덱스**

users 테이블에 데이터가 100만 건 있다고 가정하자.

```sql
SELECT name
FROM users
WHERE email = 'hello@example.com';
```

MySQL이 데이터를 찾는 방법은 크게 두 가지가 있다.

1. **전체 테이블을 읽는 방법 (Full Table Scan)**
    
    테이블에 있는 데이터를 처음부터 끝까지 확인하는 방법이다.
    
    검색 조건에 해당하는 데이터가 어디에 있는지 모르면 전체를 확인해야 한다.
    
2. **인덱스를 사용하는 방법 (Index Scan)**
    
    인덱스는 특정 값을 빠르게 찾기 위한 별도의 자료구조이다.
    
    MySQL의 InnoDB에서는 일반적인 보조 인덱스가 B+Tree 구조를 사용한다.
    
    email 컬럼에 인덱스가 있다고 가정해 보자.
    
    ```sql
    CREATE INDEX idx_users_email
    ON users(email);
    ```
    
    이제 MySQL은 전체 사용자를 하나씩 확인하지 않고 인덱스를 이용해 원하는 이메일의 위치를 찾을 수 있다.
    
    데이터가 100만 건이라고 해도 훨씬 적은 페이지를 읽고 찾을 수 있다.
    

옵티마이저는 여러 실행 방법의 예상 비용을 비교한다.

| 상황 | 예상되는 선택 |
| --- | --- |
| 전체 데이터 중 1건 조회 | 인덱스가 유리할 가능성이 높음 |
| 전체 데이터 중 90% 조회 | 전체 테이블 스캔이 유리할 수 있음 |
| 테이블에 데이터가 10건뿐임 | 전체 스캔이 더 저렴할 수 있음 |

인덱스를 사용하면 다음과 같은 과정이 필요하다.

1. 인덱스에서 원하는 데이터를 찾는다.
2. 인덱스가 가리키는 실제 데이터 페이지를 찾는다.
3. 필요한 데이터를 읽는다.

따라서 옵티마이저는 무작정 인덱스를 사용하는 것이 아니다.

조회할 데이터가 90%라면, 인덱스를 찾고 실제 데이터를 찾는 것보다 전체 스캔이 더 효율적일 수 있다.

즉, **옵티마이저는 인덱스를 사용하는 비용과 사용하지 않는 비용을 비교한다.**

#### 조인(JOIN) 순서

옵티마이저는 여러 테이블을 JOIN할 때 어떤 테이블부터 읽을지도 결정한다.

```sql
SELECT *
FROM orders o
JOIN users u
    ON o.user_id = u.id
WHERE u.id = 10;
```

두 테이블이 있다고 해보자.

- users: 100만 건
- orders: 1억 건

옵티마이저는 조건과 인덱스, 통계 정보를 바탕으로 어떤 테이블부터 접근할지 결정한다.

#### 실행 계획 (**Execution Plan)**

실행 계획은 옵티마이저가 결정한 실행 방법을 확인하는 것이다.

MySQL에서는 다음 명령어를 사용한다.

```sql
EXPLAIN
SELECT name
FROM users
WHERE email = 'hello@example.com';
```

실행 계획에서는 다음과 같은 정보를 확인할 수 있다.

| 항목 | 의미 |
| --- | --- |
| type | 테이블에 접근하는 방식 |
| possible_keys | 사용할 수 있는 인덱스 |
| key | 실제 선택된 인덱스 |
| rows | 읽을 것으로 예상하는 행 수 |
| Extra | 추가적인 실행 정보 |

예를 들어 `key`에 `idx_users_email`이 표시된다면 해당 인덱스를 사용하도록 계획했다는 뜻이다.

그러나 일반 `EXPLAIN`은 예상 실행 계획이고, 실제 실행을 측정하려면 `EXPLAIN ANALYZE`도 알아야 한다.

```sql
EXPLAIN ANALYZE
SELECT name
FROM users
WHERE email = 'hello@example.com';
```

이 명령은 쿼리를 실제로 실행하면서 실제 행 수와 실행 시간 등의 정보를 보여준다.

### **실행기 (Executor)**

옵티마이저가 만든 실행 계획을 실제로 수행하는 단계이다.

실행기는 옵티마이저의 계획에 따라 필요한 작업을 수행한다.

여기서 중요한 것은 실행기가 실제 데이터 저장소에 접근할 때 스토리지 엔진과 통신한다는 점이다.

#### Handler API

MySQL은 데이터 처리 부분을 하나의 구조로 통일하고, 실제 데이터를 저장하고 읽는 방법은 스토리지 엔진에 맡긴다.

MySQL에는 다음과 같은 스토리지 엔진이 있다.

- InnoDB
- MyISAM
- MEMORY

각 엔진은 데이터를 저장하고 관리하는 내부 방식이 다르다.

그래서 MySQL 서버와 스토리지 엔진 사이에 공통된 인터페이스를 두고 이를 Handler API라고 한다.

### **스토리지 엔진 (Storage Engine)**

실제 데이터를 저장하고 읽고 수정하는 역할을 담당하는 단계이다.

MySQL 서버 자체와 스토리지 엔진을 구분해야 한다.

MySQL 서버는 SQL을 분석하고 실행 계획을 만들고 실행을 관리한다.

반면 스토리지 엔진은 실제 데이터의 저장과 접근을 담당한다.

우리가 일반적으로 사용하는 MySQL의 기본 스토리지 엔진은 InnoDB이다.

#### Page

데이터베이스가 데이터를 읽고 쓰는 기본 단위는 **페이지(Page)**이다.

**MySQL은 행(Row)을 조회하지만, InnoDB는 페이지 단위로 데이터를 읽고 관리한다.**

페이지 단위의 이점은 한 번에 여러 행을 메모리에 올리므로 데이터 접근 효율을 높인다.

#### Buffer Pool

**디스크에서 읽은 데이터를 메모리에 보관하는 공간**이다.

컴퓨터에서 메모리와 디스크는 다음과 같은 특징이 있다.

| 구분 | 특징 |
| --- | --- |
| RAM | 빠르지만 용량이 제한적이고 휘발성 |
| SSD/HDD | 상대적으로 느리지만 대용량 데이터를 영구 저장 |

데이터를 매번 디스크에서 읽으면 성능이 떨어진다.

따라서 InnoDB는 자주 사용하는 데이터를 메모리에 올려놓고 재사용한다.

Buffer Pool은 조회 뿐만 아니라 수정에도 중요한 역할을 한다.

```sql
UPDATE users
SET name = '철수'
WHERE id = 10;
```

`UPDATE`문을 처리할 때에도 곧바로 디스크에 수정 사항을 반영하지 않는다.

InnoDB는 해당 데이터가 있는 페이지를 Buffer Pool에서 찾거나 디스크에서 읽어온다.

그 후 디스크에 반영하기 전 메모리상의 페이지를 먼저 수정하는데, 이 수정된 페이지를 **Dirty Page**라고 부른다.

그런데 메모리에만 변경된 내용을 가진 채 전원이 꺼질 수도 있다.

이러한 장애 문제를 복구하기 위해 기록해두는 로그를 **Redo Log**라고 부른다.

정리하자면 다음과 같다.

- Buffer Pool: 데이터 페이지를 캐싱하는 메모리 공간
- Dirty Page: 메모리에서 변경됐지만 디스크에는 아직 반영되지 않은 페이지
- Redo Log: 장애가 발생해도 커밋된 변경 사항을 복구할 수 있도록 기록하는 로그

## 2. 저장 장치별 속도 차이

저장 구조를 알아야 하는 이유는 디스크는 근본적으로 속도가 느리기 때문이다.

저장 장치별 속도 차이를 감각적으로 살펴보면 대략 다음과 같다.

| 어디서 읽나 | 대략적인 시간 | 사람 시간으로 환산 (메모리 = 1초) |
| --- | --- | --- |
| CPU 캐시 | ~1ns | 0.01초 |
| **메모리(RAM)** | ~100ns | **1초** |
| **SSD 랜덤 읽기** | ~수십~100µs | **약 15분** |
| **HDD 랜덤 읽기** | ~5~10ms | **약 1일** |

메모리에서 1초면 끝날 일을 SSD나 HDD에서는 최소 수십 배 이상의 시간이 걸린다.

따라서 DB 설계의 핵심은 결국 두 가지이다.

1. **디스크에 덜 가기**: 자주 쓰는 데이터는 메모리에 두기 (Buffer Pool)
2. **가더라도 덜 읽기**: 필요한 데이터만 집어 읽기 (B+Tree 인덱스)

## 3. DB가 데이터를 읽는 최소 단위

책에서 문장 한 줄만 필요하다고 하더라도, 전자책이 아닌 이상 책 한 페이지 전체를 살펴야 한다.

DB도 이와 마찬가지이다.

- **Record(레코드)**: 행 하나 (문장 한 줄)
- **Page(페이지) = Block(블록)**: 레코드 여러 개를 담는 고정 크기 상자 (책 한 페이지)

**DB는 디스크와 메모리 사이에서 항상 Page 단위로 읽고 쓴다.**

페이지는 DB마다 이름이 다를 수 있다.

DB에 따라 Page라고 하기도 하고, Block이라고도 한다.

| DB | 기본 크기 |
| --- | --- |
| MySQL InnoDB | **16KB** (`innodb_page_size`) |
| PostgreSQL | 8KB |
| Oracle | 8KB (기본값) |

따라서 200byte의 행 하나만 필요하다고 해도, InnoDB는 그 행이 포함된 16KB 페이지 전체를 읽는다.

## **4. 저장 계층 (InnoDB)**

| 계층 | 의미 |
| --- | --- |
| Tablespace | 테이블 데이터를 담는 저장 공간 |
| Segment | 특정 목적의 공간 관리 단위 |
| Extent | 연속된 페이지의 묶음(64 Pages = 1MB) |
| Page | 16KB |
| Record | 실제 데이터 한 행 |
1. **Tablespace (테이블스페이스)**

데이터를 보관하는 가장 큰 저장 공간으로 실제 디스크에 존재하는 저장 공간이다.

테이블마다 별도의 테이블스페이스 파일을 만들 수 있다.

이 파일 안에 해당 테이블의 데이터와 인덱스가 저장된다.

1. **Segment (세그먼트)**

테이블스페이스 안에서 특정 목적을 위해 사용하는 공간이다.

- 데이터 세그먼트: 실제 테이블 데이터를 저장하는 영역
- 인덱스 세그먼트: 인덱스 데이터를 저장하는 영역

InnoDB에서는 인덱스와 관련된 저장 공간을 목적별로 관리한다.

1. **Extent (익스텐트)**

64개의 페이지를 묶어 놓은 공간이다.

페이지를 하나씩 관리하는 대신 여러 페이지를 묶어서 공간을 관리하는 단위이다.

페이지를 하나씩 할당하는 것보다 여러 페이지를 묶어서 관리하면 저장 공간을 효율적으로 관리할 수 있다.

- Page 하나 = 16KB
- Extent 하나 = 64 Pages
- 16KB * 64 = 1MB

즉, Extent 하나는 일반적으로 1MB이다.

1. **Page (페이지)**

실제 데이터를 담는 기본 저장 단위이다.

데이터를 읽고 쓸 때 사용하는 기본적인 단위이기도 하다.

특정 행 하나만 조회하더라도 해당 행이 들어 있는 페이지를 읽어야 한다.

1. **Record (레코드)**

INSERT 시 만들어지는 실제 데이터 한 행이다.

## **5. 페이지의 내부 구조**

| 구성 요소 | 역할 | 비유 |
| --- | --- | --- |
| Page Header | 페이지 정보 관리 | 안내판 |
| Infimum / Supremum | 레코드의 시작과 끝 | 경계선 |
| Record | 데이터 저장 | 실제 내용물 |
| Free Space | 새로운 데이터 저장 | 빈 자리 |
| Page Directory | 레코드 빠르게 찾기 | 목차 |
| Trailer | 데이터 손상 확인 | 검사표 |
1. **Page Header (페이지 안내판)**

페이지의 기본 정보를 기록하는 곳이다.

- 이 페이지의 번호는 몇 번인가?
- 이전 페이지와 다음 페이지는 무엇인가?
- 현재 레코드는 몇 개 있는가?

1. **Infimum / Supremum (가상의 경계값)**

실제 데이터가 아니라 데이터의 시작과 끝을 표시하는 경계선이다.

- Infimum: 이 페이지에서 가장 작은 값보다 작은 가상의 레코드
- Supremum: 이 페이지에서 가장 큰 값보다 큰 가상의 레코드

1. **Record (실제 데이터)**

INSERT한 실제 데이터가 저장되는 공간이다.

레코드들은 페이지 안에 기본 키 순서에 따라 연결되어 저장된다.

1. **빈 공간 (Free Space)**

아직 데이터를 저장하지 않은 공간이다.

새로운 데이터가 INSERT되면 이 공간을 활용한다.

빈 공간이 부족하면 다른 페이지를 사용하거나 페이지 분할이 발생할 수 있다.

1. **Page Directory (페이지 목차)**

레코드를 빠르게 찾을 수 있도록 일부 레코드의 위치를 정리해 둔 목차이다.

레코드를 처음부터 하나씩 확인하지 않기 위해 존재한다.

이를 이용해 페이지 내부에서도 이진 탐색을 할 수 있다.

페이지 목차 덕분에 **메모리에 페이지가 올라오면 그 안에서 행을 매우 빠르게 찾을 수 있다.**

**느린 건 페이지를 가져오는 일이다.**

1. **Trailer (마지막 검사표)**

페이지에 저장된 데이터가 손상되었는지 확인하기 위한 체크섬 등의 정보를 보관한다.

페이지의 마지막에 위치한다.

## 6. Heap Table / B+Tree

### B-Tree / B+Tree

100만 개의 데이터에서 50만 번째의 데이터를 찾는다고 가정해보자.

처음부터 하나씩 찾는다면, 찾는 데이터가 뒤에 있을수록 그만큼 시간도 많이 늘어날 것이다.

따라서 찾는 시간을 줄이기 위한 목차를 만들어야 한다.

#### B+Tree

B+Tree는 아래와 같이 **여러 단계로 이루어진 목차**이다.

```
[1단계: 루트]               [ 100 | 200 ]
                         /      |      \
                        ▼       ▼       ▼
[2단계: 브랜치]        [1~99]  [100~199]  [200~299]
                                |
                                ▼
[3단계: 리프]         [101, 102, 103, 104 ...]  <--->  [다음 리프 노드]
```

| **단계 (Level)** | **노드 종류 (Node Type)** | **구성 및 범위 (Key / Data)** | **역할 설명** |
| --- | --- | --- | --- |
| **1단계** | **루트 노드**
(Root Node) | `[ 100 | 200 ]` | **최상위 목차**

찾으려는 데이터가 어느 범위로 가야 할지 안내하는 이정표 |
| **2단계** | **브랜치 노드**
(Branch Node) | `[ 1 ~ 99 ]`  |  `[ 100 ~ 199 ]`  |  `[ 200 ~ 299 ]` | **중간 목차**

세부 범위를 좁혀 실제 데이터가 있는 페이지로 연결 |
| **3단계** | **리프 노드**
(Leaf Node) | `101, 102, 103, 104 ...` *(↔ 양방향 연결)* | **실제 데이터 페이지**

실제 데이터(또는 주소값)가 저장되어 있으며, 옆 페이지와 연결되어 순차 탐색에 유리 |

예를 들어 150을 찾는다고 하면 다음과 같은 순서를 거친다.

1. 최상위 목차를 확인한다.
2. 150은 100~199 사이에 있으므로 해당 방향으로 이동한다.
3. 해당 범위의 페이지에서 150을 찾는다.

**범위 검색**

B+Tree의 진짜 강점은 범위 검색에 있다.

다음과 같은 SQL이 있다.

```sql
SELECT *
FROM users
WHERE id BETWEEN 100 AND 200;
```

B+Tree는 마지막 단계의 페이지들이 서로 연결되어 있다.

따라서 100이 있는 페이지를 찾은 다음, 옆 페이지로 이동하면서 읽으면 된다.

매번 처음부터 목차를 다시 찾을 필요가 없는 것이다.

그래서 다음과 같은 작업에 유리하다.

- `BETWEEN`
- `>`
- `<`
- `ORDER BY`

#### B-Tree

B-Tree는 B+Tree와의 차이는 **실제 데이터가 어디에 저장되어 있는가**에 있다.

B-Tree는 중간 페이지와 마지막 페이지 모두 실제 데이터를 저장할 수 있다.

그러나 B+Tree는 가장 마지막 페이지(리프 노드)에만 실제 데이터를 저장한다.

| 구분 | B-Tree | B+Tree |
| --- | --- | --- |
| 중간 페이지 | 실제 데이터 저장 가능 | 위치 정보만 저장 |
| 마지막 페이지 | 실제 데이터 저장 | 실제 데이터 저장 |
| 페이지 간 연결 | 일반적으로 없음 | 리프 페이지끼리 연결 |
| 범위 검색 | 상대적으로 불리 | 유리 |

실제 데이터까지 넣으면 목차 한 페이지에 들어갈 수 있는 항목이 줄어든다.

반면, 위치 정보만 넣으면 더 많은 항목을 넣을 수 있다.

그래서 InnoDB는 **B+Tree**를 기본으로 사용한다.

### **Heap Table**

Heap(힙)은 **더미**라는 뜻으로, **빈자리가 있는 곳에 순서 없이 쌓는 저장 방식**이다.

자료구조의 힙과는 무관하다.

DB마다 테이블을 저장하는 방식이 다르므로, 이 차이를 잘 알아야 한다.

#### **PostgreSQL — Heap Table 방식**

PostgreSQL은 실제 데이터와 인덱스를 별도로 저장한다.

예를 들어 회원 데이터가 아래와 같다고 해보자.

**테이블 본체 (Heap)**

| 위치 | 이름 | 이메일 |
| --- | --- | --- |
| Page 0, Slot 1 | 박지호 | jiho@ex.com |
| Page 0, Slot 2 | 최유나 | yuna@ex.com |
| Page 1, Slot 1 | 김민준 | minjun@ex.com |
| Page 1, Slot 2 | 이서연 | seoyeon@ex.com |

여기서 Heap은 데이터를 담아 놓는 테이블 본체이다.

중요한 건 앞서 언급하였듯 **PK 순서대로 정렬되어 있지 않다**는 점이다.

**이메일 인덱스 (B+Tree)**

| 이메일 | 실제 데이터 위치 |
| --- | --- |
| jiho@ex.com | (0,1) |
| minjun@ex.com | (1,1) |
| seoyeon@ex.com | (1,2) |
| yuna@ex.com | (0,2) |

인덱스는 이메일을 정렬해서 보관하고, 각 이메일이 실제 테이블의 어디에 있는지 기록한다.

여기서 `(0,1)` 같은 값이 바로 PostgreSQL의 `ctid`와 관련된 위치 정보이다.

- 앞의 숫자: Page 번호
- 뒤의 숫자: 해당 Page 안에서의 슬롯 번호

```sql
SELECT *
FROM users
WHERE email = 'jiho@ex.com';
```

위 SQL의 실행 과정은 아래와 같다.

1. **이메일 인덱스 검색** — `jiho@ex.com` 검색
2. **위치 확인** — Page 0의 Slot 1
3. **테이블 본체에서 데이터 조회** — 박지호의 실제 행을 가져옴

이처럼 인덱스에서 위치를 찾고 그 위치로 이동해서 실제 데이터를 가져온다.

또한, PK 인덱스도 이 구조에서는 테이블 본체와 별개인 인덱스이다.

#### MySQL InnoDB — Clustered Index 방식

MySQL InnoDB는 PostgreSQL과 다르게 테이블 본체가 PK 기준의 B+Tree로 구성된다.

즉, 별도의 Heap 테이블이 존재하지 않는다.

예를 들어 회원 데이터가 아래와 같다고 해보자.

**PK 인덱스 (테이블 본체)**

| PK (id) | 이름 | 이메일 |
| --- | --- | --- |
| 1 | 김민준 | minjun@ex.com |
| 2 | 이서연 | seoyeon@ex.com |
| 3 | 박지호 | jiho@ex.com |
| 4 | 최유나 | yuna@ex.com |

이 데이터가 PK 순서로 B+Tree의 리프 페이지에 저장된다.

여기서 중요한 건 리프 페이지에 PK만 있는 게 아니라 행 전체가 들어 있다는 것이다.

따라서 PK로 조회하면 한 번의 인덱스 탐색으로 실제 데이터를 가져올 수 있다.

**보조 인덱스 (별도의 목차)**

```sql
CREATE INDEX idx_email ON users(email);
```

위와 같이 이메일에 인덱스를 만들면 다음과 같은 정보가 저장된다.

| 이메일 | PK |
| --- | --- |
| jiho@ex.com | 3 |
| minjun@ex.com | 1 |
| seoyeon@ex.com | 2 |
| yuna@ex.com | 4 |

여기서 중요한 차이가 있다.

PostgreSQL은 실제 데이터의 위치를 가리키지만, InnoDB의 보조 인덱스는 PK 값을 가지고 있다.

```sql
SELECT *
FROM users
WHERE email = 'jiho@ex.com';
```

위 SQL의 실행 과정은 아래와 같다.

1. **이메일 인덱스 검색** — jiho@ex.com 검색
2. **PK 확인** — id = 3
3. **PK 인덱스 검색** — id = 3인 리프 페이지 탐색
4. **실제 행 데이터 획득** — 박지호, jiho@ex.com

이처럼 이메일 인덱스와 PK 인덱스를 차례대로 탐색해야 한다.

이를 보조 인덱스를 통한 추가적인 테이블 조회라고 한다.

**두 방식의 차이 비교**

| 비교 | PostgreSQL | MySQL InnoDB |
| --- | --- | --- |
| 테이블 본체 | Heap | PK B+Tree |
| PK 기준 정렬 | 보장하지 않음 | PK 순서 |
| PK 인덱스 | 별도 인덱스 | 테이블 본체 |
| 보조 인덱스가 가리키는 것 | 물리적 행 위치(CTID) | PK 값 |
| 보조 인덱스 조회 | 인덱스 → Heap | 인덱스 → PK 인덱스 |

## 7. Buffer Pool / Buffer Cache

### Buffer Pool

Buffer Pool은 자주 사용하는 Page를 복사해 놓는 RAM 공간이다.

데이터를 읽는 과정은 다음과 같다.

Buffer Pool 확인 : 메모리에 필요한 Page가 있는가?

- Cache Hit : 필요한 데이터가 메모리에 있다면, 디스크에 가지 않는다.
- Cache Miss : 필요한 데이터가 메모리에 없다면, 디스크에서 가져와야 한다.

예를 들어, 같은 페이지를 10번 읽는다고 가정할 때,

최초에는 메모리에 없어 디스크에서 가져오지만, 이후 9번은 Buffer Pool에서 읽는다.

### 논리적 읽기와 물리적 읽기

데이터베이스에서 성능을 분석할 때 디스크에 얼마나 자주 접근하는지 알아내고자 이 둘을 구분한다.

| 용어 | 의미 |
| --- | --- |
| 논리적 읽기 | 메모리(Buffer Pool)에서 Page를 읽는 것 |
| 물리적 읽기 | 디스크에서 Page를 읽어오는 것 |

다음과 같은 상황을 가정해보자.

- 전체 Page 읽기 요청: 1,000번
- 디스크에서 읽어온 횟수: 10번
- 나머지 990번은 메모리에서 읽음

이와 같은 경우는 Buffer Pool이 상당히 잘 작동하고 있다고 볼 수 있다.

이를 수치적으로 계산하고자 아래와 같이 Hit Ratio(적중률) 개념이 있다.

요청한 데이터가 메모리에 있어서 바로 찾은 비율이다.

> **Hit Ratio = 1 − (물리적 읽기 ÷ 논리적 읽기)**
> 

위 예시의 경우 적중률은 99%가 된다.

### 데이터 수정

데이터 수정의 경우 DB는 디스크에 있는 데이터를 곧바로 수정하지 않는다.

먼저 Buffer Pool에 있는 해당 페이지를 수정 후 나중에 디스크에 기록한다.

이때, 메모리는 수정했으나 디스크에는 수정된 내용을 아직 반영하지 않은 Page를 Dirty Page라고 부른다.

### **Midpoint LRU**

RAM은 용량의 한계가 있다.

Buffer Pool이 가득 찬 상태에서 새로운 페이지를 가져오려면 기존 페이지 중 하나를 내보내야 한다.

이때 사용하는 가장 대표적인 방식이 LRU이다.

LRU란 오랫동안 사용하지 않은 데이터를 먼저 내보내는 방식이다.

그러나 LRU의 단점은 자주 사용하는 페이지가 한 번만 사용하는 페이지에 밀려날 수 있다는 것이다.

InnoDB는 이를 보완하여 **Midpoint LRU**를 사용한다.

원리는 다음과 같다.

- Buffer Pool의 페이지를 두 그룹으로 나누어 관리한다.
- 새로운 페이지가 들어오면 old 영역에 넣는다.
    - 다시 사용되지 않으면 : old 영역에 남아 있다가 교체될 수 있다.
    - 다시 사용되면 : young 영역으로 승격될 수 있다.

즉, 오랫동안 자주 사용하는 페이지는 young으로, 새로 읽은 페이지는 old로 나누는 방식이다.

## 8. **Sequential I/O와 Random I/O**

페이지를 읽는 방법은 다음과 같이 두 가지이다.

- Sequential I/O: 연속된 Page를 순서대로 읽기
- Random I/O: 서로 떨어진 Page를 여기저기 찾아 읽기

결론부터 말하자면, **둘 중 더 빠른 방식은 연속적으로 읽는 것이다.**

그 이유는 저장장치의 특성과 관련이 있다.

HDD는 내부에 원판이 돌아가고 헤드가 움직이며 데이터를 읽는다.

1번 데이터를 읽고 바로 옆의 2번 데이터를 읽으면 헤드가 조금만 움직이면 된다.

그런데 1번 데이터를 읽고 멀리 떨어진 100번 데이터를 읽으려면 헤드가 그 위치로 이동하는 데 시간이 걸린다.

따라서 하드디스크는 **Random I/O가 느릴 수 밖에 없다.**

SSD는 HDD처럼 물리적인 헤드가 움직이지 않는다.

하지만 여전히 순서대로 데이터를 읽어오거나 다음 데이터를 미리 준비하는 데에는 **Sequential I/O**이 효율적이다.

### **Sequential I/O의 사례**

```sql
SELECT * FROM users;
```

위 SQL처럼 모든 행을 조회하는 경우에는 여기저기 이동할 필요 없이 페이지를 순서대로 읽는다.

이처럼 앞에서부터 차례대로 페이지를 읽는 방식을 **Full Table Scan**이라고 한다.

### **Random I/O의 사례**

다음은 보조 인덱스가 있는 특정 컬럼을 기준으로 행을 조회하는 경우이다.

```sql
SELECT *
FROM users
WHERE email = 'a@test.com';
```

보조 인덱스에는 실제 행 데이터가 아닌 기본 키가 저장되어 있다.

따라서 다음과 같은 과정이 발생한다.

1. 이메일 인덱스에서 해당 사용자의 기본 키를 찾는다.
2. 찾은 기본 키를 가지고 기본 키 인덱스로 이동한다.
3. 실제 사용자 데이터를 가져온다.

그런데 이메일 순서와 기본 키 순서는 서로 다를 수 있다.

결국 실제 데이터가 저장된 위치를 여기저기 찾아다녀야 할 수 있다.

이처럼 데이터가 여기저기 흩어져 있다면, Random I/O가 발생하므로 인덱스를 사용한다고 반드시 빠른 것이 아니다.

| 구분 | Sequential I/O | Random I/O |
| --- | --- | --- |
| 의미 | 순서대로 읽기 | 여기저기 찾아 읽기 |
| 비유 | 책을 처음부터 읽기 | 필요한 페이지를 찾아다니기 |
| 대표 사례 | Full Table Scan | 보조 인덱스를 통한 실제 행 조회 |
| 특징 | 대량 데이터 읽기에 유리 | 소량 데이터 찾기에 유리 |

## 9. CPU-bound / I/O-bound

### I/O-bound

데이터를 찾는 데 걸리는 시간을 줄이려면 디스크에서 데이터를 가져오는 횟수를 줄어야 한다.

다시 말해, 디스크에서 읽어야 하는 페이지 수를 줄여야 데이터를 효율적으로 찾을 수 있다.

### CPU-bound

```sql
SELECT *
FROM users
WHERE age >= 30;
```

극단적인 예시로, 메모리에 모든 데이터를 가져왔다고 가정해 보자.

디스크를 읽을 필요는 없지만 인덱스 없이 전체 검색을 한다면 처음부터 순차적으로 모두 확인해야 한다.

따라서 `users` 테이블에 100만 행이 있다면 CPU가 조건 비교 작업을 100만 번 수행할 수도 있다.

결국 CPU 입장에서는 CPU가 검사하고 계산해야 하는 행의 수를 줄어야 한다.

**차이 비교**

| 구분 | I/O-bound | CPU-bound |
| --- | --- | --- |
| 느린 이유 | 데이터를 가져오느라 | 데이터를 계산하느라 |
| 비유 | 책을 찾으러 다님 | 책을 하나씩 읽음 |
| 주요 증상 | 디스크 대기 증가 | CPU 사용률 증가 |
| 해결 방향 | 디스크 읽기 줄이기 | 처리할 행 줄이기 |

정리하자면, **I/O-bound는 데이터를 가져오는 시간이 문제이고, CPU-bound는 가져온 데이터를 처리하는 시간이 문제이다.**

## 10. SQL 실행 과정

그렇다면 SQL이 실행되면 데이터베이스는 필요한 데이터를 찾기 위해 실제로 어떤 Page들을 읽을까?

기본키(PK)를 기준으로 B+Tree를 만드는 InnoDB의 방식으로 사례를 살펴본다.

### 사례 A. 기본키(PK)로 한 건 찾기

```sql
SELECT *
FROM orders
WHERE id = 500000;
```

`id`를 기본키라고 할 때, 트리 높이가 3이라면, Root 페이지 → Branch 페이지 → Leaf 페이지를 거쳐 데이터를 찾는다.

하지만 이 3단계의 페이지 중 이미 Buffer Pool에 있는 페이지는 다시 디스크를 읽지 않는다.

이처럼 **PK 조회는 실제 데이터가 들어 있는 Leaf Page까지 바로 찾아 간다.**

### 사례 B. 보조 인덱스로 찾기

`ordered_at`에 인덱스가 있다고 해보자.

```sql
SELECT *
FROM orders
WHERE ordered_at >= '2026-03-01'
  AND ordered_at < '2026-03-02';
```

이 쿼리는 3월 1일에 주문한 데이터를 모두 가져온다.

그런데 `ordered_at` 인덱스에는 실제 주문 데이터 전체가 들어 있지 않고 다음과 같은 정보가 들어 있다.

| ordered_at | id(PK) |
| --- | --- |
| 2026-03-01 09:00 | 100 |
| 2026-03-01 09:10 | 250 |
| 2026-03-01 09:20 | 800 |
| 2026-03-01 09:30 | 1200 |

즉, **주문 날짜와 해당 주문의 PK**를 가지고 있다.

과정은 다음과 같다.

1. 보조 인덱스에서 날짜 검색
2. 조건에 맞는 기본키 수집
3. 기본키로 실제 데이터 조회

보조 인덱스만으로는 데이터를 얻을 수 없어 추가적인 데이터 접근 비용이 발생한다.

이처럼 **보조 인덱스는 PK를 찾아주고, PK 인덱스는 실제 행을 찾아준다.**

### 사례 C. 인덱스가 없는 컬럼으로 찾기

`total_price`에 인덱스가 없다면 어떨까?

```sql
SELECT *
FROM orders
WHERE total_price = 45000;
```

데이터베이스는 `total_price = 45000`인 행이 어디에 있는지 미리 알 수 없다.

따라서 PK 인덱스의 Leaf Page를 처음부터 끝까지 확인해야 한다.

이처럼 **인덱스가 없으면 전체 Leaf Page를 확인해야 한다. (Full Table Scan)**

**세가지 방식 비교**

| 구분 | A. PK 조회 | B. 보조 인덱스 조회 | C. Full Scan |
| --- | --- | --- | --- |
| 접근 방식 | PK 트리 검색 | 보조 인덱스 → PK 트리 | 전체 Leaf 순회 |
| 데이터 위치 | 바로 찾음 | PK로 다시 찾음 | 처음부터 전부 확인 |
| 읽는 양 | 적음 | 검색 결과에 따라 다름 | 전체 |
| 특징 | 효율적 | 추가 조회 비용 | 많은 데이터를 순차적으로 읽음 |

## 11. 옵티마이저

옵티마이저(Optimizer)는 SQL을 실행하기 전에 가장 효율적인 데이터 검색 방법을 선택하는 역할을 한다.

### CBO (**Cost-Based Optimizer)**

옵티마이저는 쿼리 실행 전 어떤 식으로 실행할지 예상 비용을 비교한다.

예를 들어 다음과 같은 쿼리가 있다고 가정해보자.

```sql
SELECT *
FROM orders
WHERE ordered_at >= '2026-03-01'
  AND ordered_at < '2026-03-02';
```

이 쿼리를 실행하는 방법은 여러 가지이다.

- **Full Table Scan:** 테이블 전체를 읽으며 조건에 맞는 주문을 찾는다.
- **`ordered_at` 인덱스 사용:** 날짜 인덱스에서 PK를 찾고 실제 주문 데이터를 가져온다.

비용은 크게 두 가지를 고려한다.

- **I/O 비용:** Page를 얼마나 읽어야 할까?
- **CPU 비용:** 읽은 데이터를 얼마나 처리해야 할까?

### 통계 정보 (Statistics)

옵티마이저는 쿼리를 실행하기도 전에 어떻게 비용을 계산할까?

다음과 같은 통계 정보를 활용한다.

- 테이블에 데이터가 얼마나 있을까? (전체 행, 페이지 수)
- 컬럼에 서로 다른 값이 얼마나 있을까? (Cardinality)
- 값이 어떻게 분포되어 있을까? (Histogram)

통계 정보는 다음 명령어로 확인할 수 있다.

```sql
-- 인덱스 정보 확인
SHOW INDEX FROM orders;
```

여기서 `Cardinality` 컬럼을 확인할 수 있다.

```sql
-- 테이블 통계 정보 갱신
ANALYZE TABLE orders;
```

`ANALYZE TABLE`은 통계 정보를 다시 수집하는 명령어이다.

정리하자면 옵티마이저가 실행 방법을 선택하는 과정은 다음과 같다.

1. SQL 입력
2. 통계 정보 확인
3. 여러 실행 방법의 예상 비용 계산 (I/O 비용 + CPU 비용)
4. 가장 저렴하다고 판단한 방법 선택
