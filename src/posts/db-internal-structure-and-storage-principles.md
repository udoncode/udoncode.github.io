## 1. DB의 SQL 실행 과정

애플리케이션에서 다음 SQL을 실행한다고 해보자.

```sql
SELECT name
FROM users
WHERE email = 'hello@example.com';
```

이 쿼리문은 `users` 테이블에서 이메일이 `hello@example.com`인 사용자를 찾아 이름을 반환하라는 의미이다.

그런데 데이터베이스 입장에서 실제 처리하는 과정은 다음과 같다.

1. 요청을 보낸 사용자가 접속할 수 있는 사람인지 확인한다.
2. SQL 문법이 올바른지 검사한다.
3. `users` 테이블과 `email` 컬럼이 실제로 존재하는지 확인한다.
4. 데이터를 어떤 방법으로 찾는 게 가장 효율적인지 결정한다.
5. 결정한 방법대로 데이터를 읽는다.
6. 조회 결과를 애플리케이션에 반환한다.

이와 같은 절차를 담당하는 구성 요소는 아래와 같이 나타낼 수 있다.

```
애플리케이션 (Spring, MySQL Workbench …)
│  SQL 문자열 전송
▼
┌───────────────────── MySQL 서버 엔진 ─────────────────────┐
 ① 연결 관리     커넥션 확인, 사용자 인증, 스레드 할당             
 ② 파서(Parser)  문법 검사 → 파스 트리로 쪼갬                   
                 (SELCT 오타 → 여기서 ERROR 1064)           
 ③ 전처리기      테이블·컬럼이 실제로 있나? 권한 있나?             
                 (없는 컬럼 → 여기서 ERROR 1054)             
 ④ 옵티마이저 ★  "어떻게 읽을까?" 실행 계획 수립                  
                 인덱스를 쓸까, 전체를 읽을까?                  
                 JOIN은 어느 테이블부터?                      
 ⑤ 실행기        실행 계획대로 스토리지 엔진에 데이터 요청            
└─────────────────────────┬───────────────────────────────┘
                          │ Handler API
┌─────────────────────────▼─────────────────────────────────┐
 ⑥ 스토리지 엔진 (InnoDB)                                   
    Buffer Pool(메모리)에 있으면 바로 → 빠름                 
    없으면 디스크에서 읽어 Buffer Pool에 올림 → 느림         
└───────────────────────────────────────────────────────────┘
│  결과 행 반환
▼
애플리케이션
```

| 구성 요소 | 핵심 역할 |
| --- | --- |
| 연결 관리 | 누가 요청했는지 확인 |
| 파서 | SQL 문법 분석 |
| 전처리기 | 테이블, 컬럼, 권한 확인 |
| 옵티마이저 | 가장 효율적인 실행 방법 결정 |
| 실행기 | 실행 계획 수행 |
| 스토리지 엔진 | 실제 데이터 읽기 및 쓰기 |

### **연결 관리**

데이터베이스와 대화할 수 있는 연결을 준비하는 단계이다.

SQL을 데이터베이스로 보내려면 연결이 필요하다.

이때 클라이언트와 서버 사이에 통신할 연결을 먼저 수립해야 한다.

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/shop
    username: app
    password: 1234
```

위 예시를 살펴보면 다음과 같다.

1. 스프링이 mysql로 **연결 요청**을 보낸다.
    
    이때, 접속을 요청할 mysql의 올바른 계정 정보 `username`과 `password`를 함께 보낸다.
    
2. mysql은 연결 하나당 요청 처리를 담당하는 스레드를 할당하여 **연결 수립**을 한다.
    
    이때, 스프링은 여러 개의 연결을 미리 만들어 두는데 이 연결 보관 공간을 커넥션 풀이라고 한다.
    
    | 개념 | 의미 |
    | --- | --- |
    | Connection | 애플리케이션과 DB 사이의 통신 통로 |
    | Thread | SQL 실행 등의 작업을 처리하는 실행 흐름 |
    | Connection Pool | 재사용할 연결을 보관하는 공간 |
    | SQL | 연결을 통해 DB에 전달하는 명령 |

### **파서 (Parser)**

SQL이 올바른 문법으로 작성됐는지 확인하는 단계이다.

```sql
SELECT name
FROM users
WHERE age >= 20;
```

mysql이 SQL을 전달 받을 때, 사람이 읽는 것처럼 이해할 수 없다.

SQL을 구성하는 키워드, 테이블명, 컬럼명, 조건 등을 분석하고 구조화한다.

문법 검사를 통과하면 파스 트리(Parse Tree)를 생성하여 SQL의 구문 구조를 이후 단계에 활용한다.

### **전처리기 (Preprocessor)**

SQL에 사용된 테이블, 컬럼 등이 실제로 존재하는지 확인하는 단계이다.

파서가 SQL 문법을 확인했다면 이번에는 SQL이 실제 데이터베이스에서 실행 가능한지 확인해야 한다.

문법 자체가 올바르더라도 실제 테이블과 컬럼이 존재하지 않을 수 있다.

또한, SQL을 실행하는 사용자가 해당 작업을 수행할 권한이 있는지도 확인한다.

파서와 전처리기는 다음과 같이 구분할 수 있다.

| 구분 | 파서 | 전처리기 |
| --- | --- | --- |
| 검사 대상 | SQL 문법 | 객체 및 권한 |
| 질문 | 문장이 올바른가? | 실제로 존재하고 사용할 수 있는가? |
| 오류 예시 | ERROR 1064 | ERROR 1054 |

### **옵티마이저 (Optimizer)**

데이터를 어떻게 가져오는 것이 가장 효율적일지 결정하는 단계이다.

앞에서 SQL의 검사를 마쳤다면, 실제로 데이터를 가져와야 한다.

그런데 데이터를 가져오는 방법은 여러 가지일 수 있다.

#### **인덱스**

users 테이블에 데이터가 100만 건 있다고 가정하자.

```sql
SELECT name
FROM users
WHERE email = 'hello@example.com';
```

MySQL이 데이터를 찾는 방법은 크게 두 가지가 있다.

1. **전체 테이블을 읽는 방법 (Full Table Scan)**
    
    테이블에 있는 데이터를 처음부터 끝까지 확인하는 방법이다.
    
    검색 조건에 해당하는 데이터가 어디에 있는지 모르면 전체를 확인해야 한다.
    
2. **인덱스를 사용하는 방법 (Index Scan)**
    
    인덱스는 특정 값을 빠르게 찾기 위한 별도의 자료구조이다.
    
    MySQL의 InnoDB에서는 일반적인 보조 인덱스가 B+Tree 구조를 사용한다.
    
    email 컬럼에 인덱스가 있다고 가정해 보자.
    
    ```sql
    CREATE INDEX idx_users_email
    ON users(email);
    ```
    
    이제 MySQL은 전체 사용자를 하나씩 확인하지 않고 인덱스를 이용해 원하는 이메일의 위치를 찾을 수 있다.
    
    데이터가 100만 건이라고 해도 훨씬 적은 페이지를 읽고 찾을 수 있다.
    

옵티마이저는 여러 실행 방법의 예상 비용을 비교한다.

| 상황 | 예상되는 선택 |
| --- | --- |
| 전체 데이터 중 1건 조회 | 인덱스가 유리할 가능성이 높음 |
| 전체 데이터 중 90% 조회 | 전체 테이블 스캔이 유리할 수 있음 |
| 테이블에 데이터가 10건뿐임 | 전체 스캔이 더 저렴할 수 있음 |

인덱스를 사용하면 다음과 같은 과정이 필요하다.

1. 인덱스에서 원하는 데이터를 찾는다.
2. 인덱스가 가리키는 실제 데이터 페이지를 찾는다.
3. 필요한 데이터를 읽는다.

따라서 옵티마이저는 무작정 인덱스를 사용하는 것이 아니다.

조회할 데이터가 90%라면, 인덱스를 찾고 실제 데이터를 찾는 것보다 전체 스캔이 더 효율적일 수 있다.

즉, **옵티마이저는 인덱스를 사용하는 비용과 사용하지 않는 비용을 비교한다.**

#### 조인(JOIN) 순서

옵티마이저는 여러 테이블을 JOIN할 때 어떤 테이블부터 읽을지도 결정한다.

```sql
SELECT *
FROM orders o
JOIN users u
    ON o.user_id = u.id
WHERE u.id = 10;
```

두 테이블이 있다고 해보자.

- users: 100만 건
- orders: 1억 건

옵티마이저는 조건과 인덱스, 통계 정보를 바탕으로 어떤 테이블부터 접근할지 결정한다.

#### 실행 계획 (**Execution Plan)**

실행 계획은 옵티마이저가 결정한 실행 방법을 확인하는 것이다.

MySQL에서는 다음 명령어를 사용한다.

```sql
EXPLAIN
SELECT name
FROM users
WHERE email = 'hello@example.com';
```

실행 계획에서는 다음과 같은 정보를 확인할 수 있다.

| 항목 | 의미 |
| --- | --- |
| type | 테이블에 접근하는 방식 |
| possible_keys | 사용할 수 있는 인덱스 |
| key | 실제 선택된 인덱스 |
| rows | 읽을 것으로 예상하는 행 수 |
| Extra | 추가적인 실행 정보 |

예를 들어 `key`에 `idx_users_email`이 표시된다면 해당 인덱스를 사용하도록 계획했다는 뜻이다.

그러나 일반 `EXPLAIN`은 예상 실행 계획이고, 실제 실행을 측정하려면 `EXPLAIN ANALYZE`도 알아야 한다.

```sql
EXPLAIN ANALYZE
SELECT name
FROM users
WHERE email = 'hello@example.com';
```

이 명령은 쿼리를 실제로 실행하면서 실제 행 수와 실행 시간 등의 정보를 보여준다.

### **실행기 (Executor)**

옵티마이저가 만든 실행 계획을 실제로 수행하는 단계이다.

실행기는 옵티마이저의 계획에 따라 필요한 작업을 수행한다.

여기서 중요한 것은 실행기가 실제 데이터 저장소에 접근할 때 스토리지 엔진과 통신한다는 점이다.

#### Handler API

MySQL은 데이터 처리 부분을 하나의 구조로 통일하고, 실제 데이터를 저장하고 읽는 방법은 스토리지 엔진에 맡긴다.

MySQL에는 다음과 같은 스토리지 엔진이 있다.

- InnoDB
- MyISAM
- MEMORY

각 엔진은 데이터를 저장하고 관리하는 내부 방식이 다르다.

그래서 MySQL 서버와 스토리지 엔진 사이에 공통된 인터페이스를 두고 이를 Handler API라고 한다.

### **스토리지 엔진 (Storage Engine)**

실제 데이터를 저장하고 읽고 수정하는 역할을 담당하는 단계이다.

MySQL 서버 자체와 스토리지 엔진을 구분해야 한다.

MySQL 서버는 SQL을 분석하고 실행 계획을 만들고 실행을 관리한다.

반면 스토리지 엔진은 실제 데이터의 저장과 접근을 담당한다.

우리가 일반적으로 사용하는 MySQL의 기본 스토리지 엔진은 InnoDB이다.

#### Page

데이터베이스가 데이터를 읽고 쓰는 기본 단위는 **페이지(Page)**이다.

**MySQL은 행(Row)을 조회하지만, InnoDB는 페이지 단위로 데이터를 읽고 관리한다.**

페이지 단위의 이점은 한 번에 여러 행을 메모리에 올리므로 데이터 접근 효율을 높인다.

#### Buffer Pool

**디스크에서 읽은 데이터를 메모리에 보관하는 공간**이다.

컴퓨터에서 메모리와 디스크는 다음과 같은 특징이 있다.

| 구분 | 특징 |
| --- | --- |
| RAM | 빠르지만 용량이 제한적이고 휘발성 |
| SSD/HDD | 상대적으로 느리지만 대용량 데이터를 영구 저장 |

데이터를 매번 디스크에서 읽으면 성능이 떨어진다.

따라서 InnoDB는 자주 사용하는 데이터를 메모리에 올려놓고 재사용한다.

Buffer Pool은 조회 뿐만 아니라 수정에도 중요한 역할을 한다.

```sql
UPDATE users
SET name = '철수'
WHERE id = 10;
```

`UPDATE`문을 처리할 때에도 곧바로 디스크에 수정 사항을 반영하지 않는다.

InnoDB는 해당 데이터가 있는 페이지를 Buffer Pool에서 찾거나 디스크에서 읽어온다.

그 후 디스크에 반영하기 전 메모리상의 페이지를 먼저 수정하는데, 이 수정된 페이지를 **Dirty Page**라고 부른다.

그런데 메모리에만 변경된 내용을 가진 채 전원이 꺼질 수도 있다.

이러한 장애 문제를 복구하기 위해 기록해두는 로그를 **Redo Log**라고 부른다.

정리하자면 다음과 같다.

- Buffer Pool: 데이터 페이지를 캐싱하는 메모리 공간
- Dirty Page: 메모리에서 변경됐지만 디스크에는 아직 반영되지 않은 페이지
- Redo Log: 장애가 발생해도 커밋된 변경 사항을 복구할 수 있도록 기록하는 로그
