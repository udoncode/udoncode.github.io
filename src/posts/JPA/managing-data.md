ORM에서는 크게 두 가지 개념이 가장 중요합니다.
첫 번째는 매핑입니다. 매핑은 **객체와 테이블 간의 구조적 불일치 문제를 해결**합니다. 이는 설계 시점에 다루게 되는 정적인 측면입니다.
두 번째는 데이터 관리 전략입니다. 매핑이 끝나면 **실행 중에 데이터가 어떻게 관리되는지** 이해해야 합니다. 이는 런타임 시점에 다루게 되는 동적인 측면입니다.

데이터 관리 전략은 아래와 같이 애플리케이션 성능과 동작에 직접적인 영향을 미칩니다.

- 언제 SQL이 실행되는가
- UPDATE는 언제 발생하는가
- 같은 엔티티를 여러 번 조회하면 같은 인스턴스인가

데이터를 관리한다는 건 엔티티를 어떻게 저장·조회·수정·삭제하는지, 영속석 컨텍스트 안팎으로 어떻게 다뤄야 하는지를 다루는 것입니다.




# 1. 영속성 생명주기

엔티티 클래스는 투명한 영속성을 가집니다. ‘투명하다’의 의미는 엔티티 클래스는 DB에 저장되는 객체라는 사실을 몰라도 되는 평범한 자바 객체라는 것을 의미합니다.


## 1. 엔티티 인스턴스의 상태

엔티티는 단순한 POJO 객체가 아닙니다. JPA의 내부에서는 엔티티 객체의 **상태**(**state**)를 관리합니다. 영속성 생명주기란, **엔티티 인스턴스가 살아가면서 거치는 상태들**을 의미합니다.

엔티티는 4가지 상태를 가집니다.

- **Transient (비영속)** : DB와 아무 관계 없는 상태
- **Persistent (영속)** : JPA가 관리하는 상태
- **Detached (준영속)** : JPA의 관리에서 벗어난 상태
- **Removed (삭제)** : 삭제 예정 상태

이 상태 전이를 이해하지 못하면 JPA가 왜 이상하게 동작하는지 절대 이해 못합니다.


### 비영속(Transient)

```java
Item item = new Item();
```

`new`로 생성한 객체는 모두 transient입니다. 이 객체는 DB와 아무 관련이 없습니다.

비영속 상태의 특징은 다음과 같습니다.

- DB에 저장되지 않는다
- 식별자가 없다
- JPA가 추적하지 않는다
- 참조가 끊기면 GC 대상이다

**비영속 → 영속**으로 상태 전이를 위해서는 `persist()`가 필요합니다.

```java
em.persist(item);
```


### 영속(Persistent)

DB에 저장되어 있거나 트랜잭션이 끝나면 저장될 객체입니다. 영속 객체는 항상 영속성 컨텍스트에 속해 있습니다. 또한 DB 식별자(Primary Key)를 가집니다.

영속 상태가 되는 경우는 5가지입니다.

- `persist()` 호출
- 다른 persistent 객체에서 참조
- `find()`로 조회
- JPQL 조회
- 객체 그래프 탐색


### 삭제(Removed)

삭제는 엄밀히 말해서 삭제 예정인 상태를 말합니다. 아직 DB에서 삭제되지 않았을 수도 있으며, 트랜잭션 commit 시 DELETE가 실행됩니다.

```java
em.remove(item);
```


### 준영속(Detached)

```java
Item item = em.find(Item.class, 1L);
em.close();
```

EntityManager를 닫으면 영속성 컨텍스트가 사라집니다. 그런데 item 참조는 남아 있습니다. 이게 준영속 상태입니다.

준영속 상태는 다음과 같은 특징을 가집니다.

- DB 식별자가 있다
- 더 이상 관리되지 않는다
- 변경해도 UPDATE가 실행되지 않는다
- 데이터가 오래된(갱신되지 않은) 상태일 수 있다

**준영속 → 영속**으로 상태 전이를 위해서는 `merge()`가 필요합니다. `merge()`는 새로운 영속성 컨텍스트에 병합하는 메서드입니다.

```java
em.merge(item);
```


| 상태 | DB 연결 | 추적 여부 | 변경 자동 반영 |
| --- | --- | --- | --- |
| Transient | 없음 | X | X |
| Persistent | 있음 | O | O |
| Removed | 삭제 예정 | O | commit 시 DELETE |
| Detached | 있음 | X | X |



## 2. 영속성 컨텍스트(Persistence Context)

영속성 컨텍스트는 특정 작업 단위 동안 우리가 변경한 모든 상태를 기억하는 서비스입니다. 여기서 작업 단위(Unit of Work)란 보통 **하나의 트랜잭션**을 말합니다. 영속성 컨텍스트의 범위는 작업 단위입니다.

```java
em.getTransaction().begin();
... <-- 여기서 일어나는 작업들
em.getTransaction().commit();
```

EntityManager는 하나의 영속성 컨텍스트를 가집니다. EntityManager의 생성과 종료가 곧 영속성 컨텍스트의 생성과 종료와 같습니다.

```java
EntityManager em = emf.createEntityManager(); // 생성
em.close(); // 종료
```

영속성 컨텍스트는 영속 상태의 모든 엔티티를 감시하고 관리합니다.

영속성 컨텍스트의 역할은 크게 3가지입니다.
- 변경 감지
- 1차 캐시
- 동기화


### 변경 감지(Dirty Checking)

영속성 컨텍스트는 엔티티의 이전 상태와 현재 상태를 비교하여 변경이 일어나면 UPDATE문을 따로 작성하지 않아도 commit 시 UPDATE가 발생합니다. 이를 **더티 체킹**이라고 부릅니다.

동작 원리는 다음과 같습니다.

1. 엔티티 조회 시 스냅샷 복사본을 저장
2. flush 시 비교
3. 다르면 UPDATE 실행

모든 영속 상태의 객체는 스냅샷을 가지며, flush 시 전부 비교합니다. 따라서 영속성 컨텍스트의 단위가 크다면 그만큼 메모리 부담도 커집니다.


### 1차 캐시

영속성 컨텍스트는 1차 캐시입니다. 같은 객체를 두 번 조회한다고 해서 SELECT가 두 번 실행되지 않습니다.

항상 다음과 같이 동작합니다.

1. 영속성 컨텍스트에서 조회하는 엔티티의 유무를 확인
2. 있다면, DB 연결 없이 컨텍스트에서 엔티티 반환
   없다면, SELECT를 실행하여 조회 후 컨텍스트에 보관

따라서 **SELECT는 한 번만 발생**합니다.

같은 영속성 컨텍스트 안에서는 항상 같은 결과가 나옵니다. 즉, 동일성이 보장되며 동일 DB의 행에 대한 중복 객체는 없습니다.


### 동기화(Flush)

트랜잭션 종료 시 동기화를 위한 flush를 진행합니다. flush는 DML(INSERT, UPDATE, DELETE)을 실행하는 것을 의미합니다. 데이터 일관성을 위해 변경 사항을 반영하는 과정입니다.

flush 시점은 다음과 같습니다.

- 트랜잭션 commit
- 쿼리 실행 전
- 명시적 `flush()` 호출

#### COMMIT VS FLUSH

flush는 DB에 SQL문을 전송하는 것이고, commit은 지금까지 실행된 SQL 결과를 최종 확정하는 것입니다.

| 구분 | flush | commit |
| --- | --- | --- |
| SQL 실행 | O | O |
| 트랜잭션 종료 | X | O |
| 롤백 가능 | O | X (이미 끝남) |
| 영구 반영 | X | O |
| lock 해제 | X | O |




# 2. EntityManager 인터페이스

EntityManager는 영속성 컨텍스트를 관리하는 중심 인터페이스입니다.
다음과 같이 크게 3가지 역할을 합니다.

1. **CRUD**
2. **쿼리 실행(JPQL, Criteria Query, Native SQL)**
3. **영속성 컨텍스트 관리**

하나의 작업 단위 기준으로 작업을 진행하며, 코드 패턴은 다음과 같습니다.

```java
EntityManagerFactory emf =
        Persistence.createEntityManagerFactory("");

// . . .
EntityManager em = emf.createEntityManager();

try {
    em.getTransaction().begin();
    // . . .
    em.getTransaction().commit();
} catch (Exception ex) {
    // 트랜잭션 롤백, 에러 핸들링
} finally {
    if (em != null && em.isOpen())
        em.close();
}
```

정리하자면, 하나의 작업 단위는 이런 흐름입니다.

1. EntityManager를 만든다
2. 트랜잭션을 시작한다
3. 그 안에서 엔티티를 조회/수정/저장/삭제한다
4. 트랜잭션을 커밋한다
5. EntityManager를 닫는다

작업 단위는 트랜잭션 단위이므로, 원자적인 특징을 가집니다. 트랜잭션의 범위는 `begin()`부터 `commit()`이며, 영속성 컨텍스트의 범위는 EntityManager가 닫히는 `close()`까지 입니다. 보통 요청당 하나의 영속성 컨텍스트를 만듭니다. 또한, commit 시 더티 체킹 → flush → SQL 실행 과정이 이루어집니다.


### 데이터 영속화

`new`를 통해 비영속 상태의 엔티티를 영속 상태로 만드려면 `persist()`를 호출합니다. 여기서 중요한 것은 `persist()` 자체가 **반드시 즉시 INSERT를 의미하지는 않는다**는 것입니다. `persist()`는 객체를 저장 대상으로 등록하는 역할이며, commit 시점에 flush(SQL 동기화)가 발생한 이후 INSERT SQL이 발생합니다. 단, **식별자 생성 전략**에 따라 `persist()` 호출 시점에 즉시 INSERT가 나갈 수 있습니다.(pre-insert 방식)

- `persist()` : 이 객체를 저장 대상으로 등록
- `flush()` : 실제 SQL 동기화
- `commit()` : 트랜잭션 최종 확정


### 데이터 조회

엔티티를 조회하려면 `find()`를 호출합니다. `find()`는 ID로 조회하며, 없으면 null을 반환합니다. 조회한 객체는 영속 상태이며 영속성 컨텍스트에 등록됩니다.

만약, 영속성 컨텍스트 안에 같은 엔티티 타입과 같은 식별자를 가진 객체가 이미 있다면 DB에 접근하지 않습니다. 즉, DB에 접근하기 전 컨텍스트 캐시를 확인하여 해당 엔티티가 존재하는지 먼저 조회합니다.

조회한 엔티티를 수정하면 더티 체킹(스냅샷과 현 객체 상태 비교) 후 Flush 시점에 UPDATE가 실행됩니다. 이 때 UPDATE문은 변경되지 않은 컬럼도 포함되는데 SQL을 미리 생성하여 캐싱하기 위함입니다.


### 프록시 얻기

경우에 따라서는 엔티티의 모든 데이터를 당장 읽어오지 않아도 될 수 있습니다. DB에 접근하지 않고 참조만 얻고 싶은 경우 `getReference()`를 이용할 수 있습니다.

해당 메서드는 DB 조회 없이 프록시를 반환합니다. 프록시는 ID 값만 가지고 있는 비어 있는 껍데기 객체로, 실제 데이터가 필요한 시점에 `getter()`를 호출하면 SELECT가 실행되어 초기화됩니다. 즉, 즉시 로딩이 아니라 지연 로딩입니다. 그러나 만약 해당 ID를 가진 엔티티가 영속성 컨텍스트에서 관리되고 있다면, 프록시 대신 해당 영속 상태의 객체를 반환합니다.

프록시는 식별자 값만 지닌 객체이므로, `getId()`와 같은 식별자 getter는 보통 SELECT 없이 호출할 수 있습니다. 프록시는 애초에 ID를 가진 엔티티를 대신하는 정보이기 때문입니다.

#### EntityNotFoundException

실제 DB 행에 존재하지 않으면, 프록시를 초기화하는 시점에서 예외가 터집니다. 다시 말해, 사용 시점에서 `getter()` 메서드를 호출하면 DB를 조회하게 되고, 이때 행이 존재하지 않으므로 `EntityNotFoundException`이 발생합니다.

#### LazyInitializationException

영속성 컨텍스트가 닫히면, 내부에서 관리되던 프록시를 포함한 엔티티는 detached 상태가 됩니다. 즉, 더 이상 현재 EntityManager가 관리하지 않고 필요한 순간 DB에서 데이털르 가져다줄 연결 통로도 사라집니다.

이렇게 컨텍스트가 닫힌 상태에서 초기화되지 않은 프록시에 접근하면 `LazyInitializationException` 예외가 발생합니다. 의미를 정리하자면 다음과 같습니다.

- 지금 이 객체는 지연 로딩 프록시인데,
- 실제 데이터가 아직 로딩되지 않았고
- 그런데 이미 영속성 컨텍스트는 닫혀버려서
- 더 이상 DB에서 로딩할 수 없다

이를 해결하려면 컨텍스트를 닫기 전에 미리 프록시를 초기화하면 됩니다. 즉, getter를 호출하는 것입니다.


### 데이터 비영속화

엔티티를 DB에서 삭제하고 싶을 때, EntityManager의 `remove()`를 호출합니다.

`remove()`를 호출한다는 것은 두 가지를 의미합니다.

- 엔티티를 removed 상태로 만든다.
- 트랜잭션 종료 시 DELETE 실행을 예약한다.

중요한 점은 `remove()`를 호출하면 그 즉시 DB에서 행이 삭제되는 것이 아니라, 삭제 예약(queue)이 걸립니다. 영속성 컨텍스트는 `remove()`가 호출되면, 해당 엔티티를 삭제 대상으로 등록합니다. 그후, 트랜잭션이 flust/commit이 되어야 비로소 DELETE가 실행되고 DB의 행이 삭제됩니다. 따라서 flush 이전에는 같은 컨텍스트 안에서 `persist()`를 통해 삭제를 취소할 수 있습니다.

프록시에 `remove()`를 호출하면 해당 프록시에 대해 SELECT를 실행합니다. **생명주기 상태가 바뀌는 순간**에는 엔티티가 완전히 초기화되어 있어야 하기 때문입니다. 따라서 실제 엔티티를 로딩 후 삭제 작업을 거치게 됩니다.


### 데이터 새로고침

다른 트랜젝션에 의해 DB의 행이 수정된 경우가 있습니다. 이와 같은 상황에서 refresh()를 실행하면, 다음과 같이 동작합니다.

- SELECT 실행
- DB 값 다시 조회
- 메모리 덮어쓰기

메모리를 DB 상태로 덮어쓰기 때문에 변경사항을 되돌리고자 하는 취소 기능을 구현할 때 사용할 수 있습니다.


### 영속성 컨텍스트의 캐시

영속성 컨텍스트에는 모든 영속 상태의 엔티티와 스냅샷이 포함되어 있습니다. 따라서 한 번에 대량의 건수를 조회하면 OutOfMemory의 원인이 됩니다. 따라서 **수정하지 않을 엔티티를 굳이 영속 상태로 둘 필요가 없습니다.**

영속성 컨텍스트는 이를 자동으로 정리해주지 않기 때문에 삭제를 하려면 다음 2가지 옵션을 사용할 수 있습니다.

- `detach()`

  특정 엔티티를 제거합니다.

- `clear()`

  전체 엔티티를 제거합니다.





# 3. 준영속 상태 다루기

준영속 상태는 영속성 컨텍스트가 닫히거나 `detach()`를 명시적으로 호출하는 경우 발생합니다. 영속성 컨텍스트가 닫혔다는 의미는 인스턴스의 동일성을 보장하지 못함을 의미합니다. 다시 말해 영속 상태를 벗어나면 더 이상 영속성 컨텍스트가 관리해주지 않습니다.

`detach()` 메서드는 다음과 같은 경우에 유용합니다.

- 일부 객체만 영속성 컨텍스트에서 제거하고 싶을 때
- 대량 조회 후 메모리를 절약하고 싶을 때
- 변경 추적을 끄고 싶을 때

이 메서드의 장점은 영속성 컨텍스트를 `close()` 하지 않은 상태로 특정 객체만 분리할 수 있다는 점입니다.
이렇게 분리된 객체를 다시 DB에 반영하려면 `merge()`를 이용합니다.
`merge()`는 다음과 같이 동작합니다.

**1. 동일 ID의 영속 인스턴스가 컨텍스트에 있는가?**
   → 있으면, 그 객체를 사용
   → 없으면, DB 조회

**2. DB에 행이 존재하는가?**
   → 있으면, DB에서 객체 로딩 후 준영속 객체 값을 영속 객체에 복사
   → 없으면, 새 객체 생성 후 준영속 객체 값 복사하여 INSERT 예정

핵심은 merge()를 한다고 해서 컨텍스트가 해당 객체를 보관하는 것이 아니라 **해당 객체의 값을 복사한 새로운 영속 객체를 반환한다**는 것입니다.



#### 상태 흐름

최종적으로 상태 흐름은 다음과 같이 정리할 수 있습니다.

```markdown
transient
   ↓ persist / merge
persistent
   ↓ detach / close
detached
   ↓ merge
persistent
   ↓ remove
removed
```
